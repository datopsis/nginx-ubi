## Handing off to `datopsis/container-hardening`

The control work in Package 5 is the seed of a standard meant to apply across
every Datopsis container build rather than to this image alone. That standard
moves to its own repository.

### What transfers

These are reusable as they stand, and were built to be:

- **The origination model** — six values, a responsible role that must match,
  and the rule that only `image-owned` asserts the project satisfies anything.
  This is what makes a host expectation safe to include without it reading as a
  claim. See [CONTROL-MODEL.md](CONTROL-MODEL.md).
- **The pinned-source discipline** — every catalogue and guidance document
  fixed by URL, release, and SHA-256 before any mapping is made against it, so
  a mapping is always against a known revision and a replaced package is
  visible rather than silent.
- **The verification-pointer rule** — an `image-owned` control must cite a
  requirement identifier that exists in the product's own requirement tree.
  This is what stops a control asserting an obligation the product never
  stated, and it is the part most worth carrying forward.
- **The structural checks** — `tests/test_control_model.py`, which are
  product-independent apart from the requirement-tree lookup.
- **ADR-0009 and ADR-0010** — the catalogue and applicability reasoning.

Two notes carried from the work here. The GPOS SRG filename uses the token
`U_GPOS_`, not the expanded name — the expanded form 404s at every release.
And DISA serves superseded releases alongside current ones (`U_GPOS_V2R7_SRG.zip`
still returns 200), so a 200 is not evidence that a release is current; the
adjacent-release probe is what establishes that.

These are recorded rather than added to this repository's register. Whether the
GPOS SRG becomes a cross-reference for this image — DoD guidance uses it for
image-level controls where no container-specific STIG exists — is a decision
that should follow the new repository's model rather than precede it.

### What the new repository still has to decide

- How an SRG or STIG converts to reviewable Markdown, and whether that
  conversion is generated and checked for drift the way the trace matrix is
- How a per-application profile selects and tailors from the standard, since
  the applicability determination in ADR-0010 is exactly the kind of judgement
  that will differ per image
- Whether the control spine lives in the standard, in each image repository, or
  is generated into each from the standard

## Conventions that outlive this snapshot

- A completed roadmap item is deleted from `docs/ROADMAP.md`, not checked off,
  so the file is always the remaining work.
- Decisions that are expensive to reverse, give up something a reader expects,
  or whose reasoning is not recoverable from the code go in `docs/adr/`.
- Where a decision is enforced by a test or CI gate, the record says so.
  Unenforced decisions decay quietly.
